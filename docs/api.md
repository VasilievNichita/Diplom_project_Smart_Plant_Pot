# API и подключение ESP32

Версия протокола 1 с расширениями v0.3. Сейчас сервер работает на ПК, без облака и без подключённого оборудования. База по умолчанию — `data/folium.sqlite`. Для сервера нужен Node.js 24+. [Прошивка ESP32](../firmware/README.md) реализует этот контракт; [схема и сборка](hardware-assembly.md) подготовлены для будущих физических испытаний.

## Что уже можно проверить

Из каталога `site`:

```sh
npm test
npm run simulate
```

Симулятор создаёт отдельный сервер на случайном локальном порту и базу в памяти. Передаёт два измерения, запрашивает дозу, получает команду ровно один раз и подтверждает имитацию выполнения. Адрес рабочего сервера и путь к настоящей базе ему передать нельзя. Это проверка программного обмена, а не эксперимент с растением.

## Подключение настоящего контроллера позже

1. Запустить сервер через `npm start` или `start-site.cmd`.
2. В другом терминале, из `site`, выполнить `npm run provision-device -- esp32-main`. Ключ будет записан в `private/esp32-main.json` вне публичного сайта. Не публиковать этот файл и не отправлять его в чат. Ключ не выводится в терминал. Повторная регистрация блокируется; инструмент смены потерянного ключа пока не реализован.
3. Остановить сервер. Для доступа контроллера из доверенной домашней сети задать отдельный адрес слушателя. Например, в PowerShell из `site`:

```powershell
$env:FOLIUM_DEVICE_HOST = '0.0.0.0'
$env:FOLIUM_DEVICE_PORT = '4174'
npm start
```

4. В прошивке указать локальный IP ПК, порт 4174 и ключ из приватного файла. Пример адреса-заготовки: `http://<LAN-IP-PC>:4174`. Проброс портов роутера не нужен. Если потребуется правило Windows Firewall, ограничить его частной сетью и устройством стенда. Сейчас сетевой слушатель не включён и правила брандмауэра не изменялись.
5. Контроллер получает конфигурацию, передаёт текущие показания каждые 15–30 секунд и опрашивает команды. Вначале насосы физически выключены.
6. Измерить калибровку каждой пробы на образцах субстрата и расход каждой помпы мерной ёмкостью. В «Мои наблюдения → Настройки» сохранить калибровку и пределы. Получить свежие измерения уже после изменения привязки/калибровки.
7. Только после проверки трубок, поддонов, питания, датчика уровня и локального ограничителя времени разрешить команды. Начать с малой проверочной дозы под наблюдением.

Управление через браузер по-прежнему доступно только на самом ПК. Порт 4174 принимает только API устройств. Для доступа к сайту с телефона потребуется отдельный этап: аутентификация оператора и защищённое размещение. HTTP-слушатель для ESP32 предназначен для доверенного тестового LAN; перед выходом в недоверенную сеть нужны TLS и контроль доступа.

## API браузера

Хранение ручной разметки фото и экспорт выбранного набора описаны в [контракте фотоосмотров](photo-api.md). Интерфейс разметки выпускается отдельно; модель ещё не обучалась.

Все тела — JSON. Изменяющие запросы требуют `Content-Type: application/json` и `X-Folium-Client: web`. Сервер также проверяет Host и Origin. Клиент выполняет запросы с того же адреса, на котором открыт сайт. Это локальная однопользовательская модель, а не система аккаунтов.

| Метод и путь | Назначение |
|---|---|
| `GET /api/health` | Работоспособность API |
| `GET /api/bootstrap?mode=demo` | Состояние сайта, назначения обоих режимов, журнал выбранного режима, статус устройств и команд |
| `GET /api/events?mode=real&before=<seq>&plantId=cactus` | Журнал, до 200 записей; `next` — курсор следующей страницы |
| `POST /api/events` | Ручное наблюдение со стабильным `id`, `mode`, `plantId`, `type`, `note` и необязательными измерениями |
| `PUT /api/prefs` | Сохранение `email` и `telegram`; отправка уведомлений не выполняется |
| `POST /api/import` | Идемпотентный импорт прежнего состояния браузера; оригиналы остаются в браузере |
| `GET /api/photos?mode=real` | Метаданные фотографий |
| `POST /api/photos` | `id`, `mode`, `plantId`, `note`, `name`, `mime`, `base64`, необязательная дата |
| `GET /api/photos/<id>` | Файл фотографии |
| `DELETE /api/photos/<id>` | Удаление фотографии с сервера |
| `PUT /api/channels/1/assignment` | `mode`, `plantId`, `expectedRevision`; меняет назначение и выключает реальный канал |
| `POST /api/plants/chlorophytum/calibration` | `dryADC` и `wetADC`: целые 0–4095, разница минимум 100 |
| `PUT /api/channels/1/config` | Измеренный расход, ограничения и разрешение команд |
| `GET /api/measurements?plantId=chlorophytum&limit=500` | Телеметрия; необязательные `since` в ISO 8601 и `before` из поля `next`, максимум 2000 строк |
| `POST /api/commands` | Поставить ограниченную дозу в очередь для настоящего канала |
| `POST /api/disarm` | Запретить новые команды, отменить ожидающие |
| `POST /api/commands/<id>/reconcile` | После личной проверки неизвестного результата: `pumpsStopped: true`, заметка минимум 5 символов |
| `GET /api/export/events.csv?mode=real` | Весь журнал выбранного режима; формулы в ячейках экранируются |
| `POST /api/backup` | Полный снимок SQLite с фотографиями и телеметрией; тело `{}` |
| `POST /api/devices` | Однократная регистрация контроллера локальным скриптом |

Пример настройки канала после калибровки и получения свежей телеметрии:

```json
{
  "expectedRevision": 2,
  "pumpMlPerSecond": 2.0,
  "maxDoseMl": 30,
  "dailyLimitMl": 100,
  "cooldownSeconds": 1800,
  "armed": true
}
```

Числа в примере иллюстрируют формат. Их нельзя считать измеренными расходами или нормами ухода. Реальное значение `expectedRevision` нужно получать из сервера.

## Аутентификация устройства

Каждый запрос устройства содержит `Authorization: Bearer <device-token>`. В API нет публичного метода чтения ключей. Таблица устройств хранит только хеш ключа. Порт устройства не предоставляет API браузера или файлы сайта.

`GET /api/device/config` возвращает `deviceId`, `protocol`, `serverTime`, `maxRuntimeMs`, `capabilities` и два реальных канала. У каждого: `id`, `plant_id`, `sensor_id`, `revision`, `armed`, калибровка и ограничения. Поле `armed` разрешает приём ограниченных команд; оно не запускает насос само по себе. Прошивка v0.3 требует расширения `measured-duration-v1` и `command-resolution-v1`; старый сервер без них не разрешит ей включить выход.

## Пакет измерений

`POST /api/device/telemetry`:

```json
{
  "bootId": "unique-id-for-this-boot",
  "sequence": 1,
  "reservoirOk": true,
  "firmware": "esp32-folium-0.1",
  "temperature": 23.1,
  "humidity": 48.0,
  "lux": 350,
  "readings": [
    {"channelId": 1, "bindingRevision": 2, "sensorId": "S-01", "raw": 2200, "quality": "ok"},
    {"channelId": 2, "bindingRevision": 2, "sensorId": "S-02", "raw": 2000, "quality": "ok"}
  ]
}
```

- Новый `bootId` на каждую загрузку; возрастающий целочисленный `sequence`. Повторная отправка использует тот же пакет без изменений. Идентичный повтор возвращает `duplicate: true` и не обновляет время свежести. Другие данные с тем же номером отклоняются.
- `bindingRevision` и `sensorId` берутся из актуальной конфигурации. Аналоговая проба не определяет свою личность; физическую привязку подтверждает человек.
- `quality`: `ok`, `disconnected` или `error`. Для отсутствующего показания передать `raw: null`, не ноль. Не включать старые показания в пакет как новые. Для архивной загрузки в будущем нужен отдельный API.
- Температура, влажность и освещённость необязательны. `reservoirOk` обязателен. Неизвестный уровень воды нельзя отправлять как `true`.
- Сервер сохраняет время приёма. Необязательное `observedAt` в ISO 8601 допускается при расхождении с сервером не более двух минут.
- Расчёт индекса: `100 × (raw − dryADC) / (wetADC − dryADC)`. Это относительный индекс для данной пробы и субстрата, не объёмная влажность. Вне диапазона сохраняется `quality: out_of_range`, а не искусственно допустимый процент. Без калибровки — `uncalibrated`.
- Пакет проверяется и записывается одной транзакцией. Неверная привязка одного канала отклоняет весь пакет.

## Полив и подтверждение

Оператор создаёт запрос `POST /api/commands`:

```json
{
  "mode": "real",
  "requestKey": "unique-request-id",
  "channelId": 1,
  "expectedRevision": 2,
  "volumeMl": 10
}
```

Повтор запроса с тем же ключом и содержимым вернёт прежнюю команду. Команда не создаётся в демонстрационном режиме. Проверяются калибровка, разрешение канала, показания не старше 60 секунд, вода, доза, пауза и суммарный запрошенный объём за последние 24 часа. Максимум 30 секунд непрерывного включения в одной команде. Результат запроса означает постановку в очередь, а не полив.

Контроллер вызывает `POST /api/device/commands/claim` с `{}`. Ответ — `{ "command": null }` либо одна команда с `id`, `channel_id`, `plant_id`, `sensor_id`, `binding_revision`, `duration_ms`, `requested_ml`, `expires_at`. Сервер повторно проверяет условия и выдаёт команду **один раз**. Срок получения — 30 секунд. Потерянный ответ не приводит к повторной выдаче: будет нужен разбор неизвестного результата.

Контроллер обязан:

1. Проверить срок, привязку, локальный датчик уровня и пробу.
2. Проверить `id` в энергонезависимом журнале команд и записать принятие до включения насоса.
3. Включить нужный канал на ограниченное `duration_ms`; прервать при локальной ошибке. Таймер отключения не должен зависеть от Wi-Fi или сервера.
4. Остановить насос, сохранить результат и отправлять одинаковое подтверждение до успешного ответа сервера.
5. После перезагрузки оставить насосы выключенными и не возобновлять прерванную команду автоматически.

`POST /api/device/commands/<id>/result`:

```json
{"status":"completed","actualDurationMs":5000,"note":"Completed by local timer"}
```

При отказе — `status: failed` и фактическая длительность выхода, в том числе 0. Для `completed` допускается задержка отключения до 50 мс сверх команды. Большее превышение принимается только как `failed` и снимает разрешение обоих каналов. Диапазон **отчёта об ошибке** до 86 400 000 мс позволяет сохранить правду о сбое; диапазон **команды** по-прежнему максимум 30 000 мс. Длительность нельзя обрезать до заданной ради прохождения проверки. Подтверждение идемпотентно. В журнал записывается оценка объёма по времени и расходу, а поле реально измеренного объёма остаётся пустым. Суточный бюджет учитывает большее из запрошенной дозы и оценки по известному времени выхода.

`GET /api/device/commands/<id>` возвращает только команду данного устройства: `{id,status,resolution}`. `resolution` - сохранённый результат или `null`. После ручного разрешения неизвестного исхода содержит `{reconciled:true,note}` без выдуманного времени/объёма. При обнаружении записи `accepted` после перезагрузки прошивка **не отправляет нулевую длительность** и не повторяет импульс. Она передаёт телеметрию с новым `bootId`, ожидает ручной проверки и читает решение этим методом. Локальная блокировка снимается только при `reconciled:true` и физическом OFF. Известный, сохранённый до сбоя результат вместо этого повторно отправляется без изменений.

Доставленная команда без результата через срок плюс 60 секунд становится `unknown`. Она блокирует новые команды и замену горшка. После личной проверки и остановки насосов оператор разрешает неопределённость в настройках; каналы остаются выключенными. Отказ и неизвестный результат консервативно учитываются в бюджете по полной запрошенной дозе.

## Ошибки и ограничения

Ответы об ошибках: `{ "error": "код" }`. 400 — неверные данные, 401 — ключ устройства, 403 — недопустимый источник/заголовки, 404 — неизвестный ресурс, 409 — конфликт или блокировка полива, 413 — слишком большой запрос, 415 — неверный формат. При 409 не повторять полив с новым ключом вслепую; перечитать состояние и причину.

Пока нет автоматического расписания, обучения модели, OTA-прошивки, удалённых аккаунтов, TLS-терминации, отправки сообщений и проверки настоящего насоса. До автономного использования нужна аппаратная проверка всех локальных защит, включая потерю сети, перезагрузку и заклинивание исполнительного устройства.
